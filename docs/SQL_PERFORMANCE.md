# SQL 성능 평가 및 개선

## 평가 범위와 환경

설정된 Neon DB에서 홈 화면 쿼리와 목록/건수 조회 방식을 읽기 전용으로 비교했다. 테이블 통계상 일정 22건, 게시글 4건, 회원 5건, 코트 12건이다. 작은 데이터에서의 측정이며 대규모 부하 테스트는 아니다. DB 데이터와 인덱스는 변경하지 않았다.

`pg_indexes` 조회 결과 게시판 `(bbs_type_id, created_at DESC)`, 일정 `(start_datetime)`, 참여자 `(event_id, status)` 등 주요 인덱스가 이미 있었다. 현재 규모와 실행 시간으로는 인덱스를 추가할 근거가 부족하다.

측정은 로컬 개발 환경에서 DB까지의 왕복 시간이다. 배포된 서비스의 응답 시간이나 브라우저 렌더링 시간은 포함하지 않는다. 테이블 통계의 건수는 추정치이며, 실제 변경 전 일정 조회 결과는 22행이었다.

## 측정 결과

최종 코드의 SQL을 직접 추출해 재측정했다. 각 방식 워밍업 후 실행 순서를 번갈아 바꾸며 7회 측정했다.

| 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 홈 SQL / HTTP 요청 수 | 4 | 2 |
| 홈 일정 최대 반환 행 | 100 | 2 |
| 홈 DB 조회 중앙값 | 234.21ms | 225.19ms |
| 홈 DB 조회 최소~최대 | 224.31~672.15ms | 219.14~616.45ms |
| 반환 데이터 JSON 크기 | 10,999 bytes | 423 bytes |

현재 DB에는 종료되지 않은 일정이 없으므로 변경 후 일정은 0행, 공지는 2행이다. JSON 크기는 드라이버가 반환한 값을 직렬화한 크기이며 HTTP 헤더나 압축을 반영한 전송 바이트가 아니다. 반환량 감소율은 실제 데이터와 진행 중 일정 수에 따라 달라진다.

최종 측정의 첫 `SELECT 1` 요청은 735.51ms였다. 이를 DB 콜드 스타트로 단정할 수는 없다. 개별 `EXPLAIN (ANALYZE, BUFFERS)` 실행 시간은 0.029~0.077ms, 계획 시간은 0.046~0.171ms였다. 이번 환경에서는 DB 연산보다 연결/네트워크/드라이버를 포함한 왕복 비용의 영향이 크다. 7회 표본의 중앙값 개선은 약 4%로 작고 변동 폭도 커서, 일정한 체감 속도 향상을 보장하는 수치로 해석하면 안 된다.

공지 목록과 COUNT의 병렬 HTTP 요청은 중앙값 229.09ms, 단일 읽기 전용 트랜잭션은 230.71ms였다. 요청 합치기만으로 유의미한 개선이 확인되지 않아 일반 페이지네이션 쿼리는 유지했다.

## 적용한 변경

- 홈 일정은 `end_datetime >= NOW()` 조건과 시작 시간 오름차순을 SQL에서 적용하고 2건만 조회한다. 진행 중 일정도 포함한다.
- 기존에는 시작 시간 내림차순 100건을 받은 뒤 앱에서 필터/정렬했다. 예정 일정이 100개를 넘으면 가까운 일정이 잘릴 수 있었던 문제도 해결했다.
- 홈의 전체 일정 수와 공지 수 COUNT를 제거했다. 페이지 수를 표시하지 않는 홈 전용 조회를 서비스 → 리포지토리 → 쿼리 계층으로 추가했다.
- 공지의 게시판 구분과 노출 시작/종료 조건, 작성자가 없는 경우의 LEFT JOIN은 유지했다.
- 정렬 값이 같을 때 PK로 순서를 결정한다. 일반 목록의 페이지네이션 API 계약은 바꾸지 않았다.

## 검증 및 재실행

`.env.local` 또는 환경 변수의 `DATABASE_URL`을 사용한다. URL, 자격 증명, 조회된 사용자 데이터는 출력하지 않는다. DB에 연결할 수 있는 환경에서 실행한다.

```sh
npm run db:benchmark
npm run db:check
```

`db:benchmark`는 이전 쿼리와 실제 변경 후 SQL을 비교하고 계획/실행 시간, 왕복 시간, 반환 크기를 출력한다. SQL 실행 계획 측정에는 5초 statement timeout, HTTP 요청에는 10초 timeout을 둔다. 초기 두 측정 시도는 연결 오류로 중단되어 표본에서 제외했다. 완료된 반복 측정에 재시도 결과를 섞지는 않았다.

`db:check`는 실제 쿼리를 읽어 CTE 테스트 데이터로 다음 5가지를 검증한다. 모두 통과했다. 읽기 전용 트랜잭션이며 실제 테이블을 수정하지 않는다.

1. 100개 초과 예정 일정에서 진행 중 일정과 가장 가까운 일정 선택
2. 종료된 일정만 있을 때 빈 결과
3. 시작 시간이 같은 일정의 안정적인 순서
4. 공지 노출 기간 경계, 비노출/다른 게시판 제외, 작성자 누락 처리
5. 공지 최대 반환 건수 제한

변경 파일 ESLint 검사 통과. 전체 TypeScript 검사는 기존 오류 14건으로 실패하며, 기존 `post.repository.ts`의 사용되지 않는 필터 인자 불일치도 여기에 포함된다. 이번에 추가한 코드에서 새 타입 오류는 보고되지 않았다.

## 다음 평가 지점

배포 환경에서도 왕복 시간이 크다면 앱 함수와 DB의 실제 리전 배치를 먼저 비교한다. 현재 로컬 측정만으로 배포 리전 변경을 결정하지 않는다. 회원/일정/코트 데이터가 커지면 해당 화면의 대표 매개변수와 `EXPLAIN (ANALYZE, BUFFERS)`로 재측정하고, 정렬과 필터를 함께 지원하는 인덱스 및 깊은 OFFSET 페이지를 평가한다.

참고: PostgreSQL의 EXPLAIN 실행 시간에는 클라이언트로 결과를 보내는 네트워크 시간이 포함되지 않는다. [PostgreSQL 공식 문서](https://www.postgresql.org/docs/17/using-explain.html). Neon의 `transaction()`은 여러 쿼리를 단일 HTTP 요청으로 전송한다. [Neon 드라이버 공식 문서](https://github.com/neondatabase/serverless/blob/main/README.md).
